# ゲームデザインの考え方（全ゲーム共通）

作成日: 2026-09-26

ゲームを作る・直すときに、先に読む。ごほうび・ステージ・強化の決まりは [03-rewards-and-games.md](03-rewards-and-games.md) にあり、そちらが優先。このドキュメントは「どういうゲームにするか」を決めるときの考え方と、ゲームごとの設計書の書き方をまとめる。

## 設計書の置き場所と形

- **1つのゲームにつき1つの設計書**: `docs/games/<id>.md`（ひな形は [games/_template.md](games/_template.md)）
- あそびラボの候補は [04-game-candidates.md](04-game-candidates.md) に書く。正式なゲームにするときに `docs/games/<id>.md` を作る
- 設計書は「デザイン」と「仕様」の2部に分ける

| 部 | 節 | 書くこと |
|---|---|---|
| デザイン | ねらい | だれに・どんな気持ちにさせたいか・1回の長さ・勉強とのつながり |
| | 好まれると考えているポイント | 子どもが遊び続ける理由の仮説。**根拠**（参考にしたゲーム・ユーザーの指摘）と、**確かめたか**（未 / bot のみ / 子どもで確認） |
| | 仕組みと意図 | 仕組みごとに「なぜそうしたか」と「ためして、やめたこと」 |
| | バランス | 考え方（どの軸を何で決めるか）、主な数値とコードの場所、調整の進め方、調整の記録（版ごとに、変えたこと・きっかけ・結果）、わかっている問題 |
| 仕様 | 世界観・遊び方・敵・ステージ・成長・画面・画像・ファイル | いまの作りの説明（コードを読まなくてもわかるように） |

- `npm test`（`src/games/registry.test.ts`）が、登録したゲームすべてに設計書があり、デザインの4つの節がそろっているかを確かめる

## 作る・直すときの流れ: デザイン → 実装

なんとなく作らないため、また設計書と実装がずれないように、**いつも設計書を先に書く**。

1. **設計書の「デザイン」を先に書く / 直す**
   - 何を変えるか、なぜ変えるか（どの「好まれると考えているポイント」のためか。新しいポイントなら根拠も）
   - バランスへの影響（どの数値をどう変えるつもりか）
   - ユーザーの指摘がきっかけなら、指摘をそのまま根拠に書く
2. 決めかねること（遊び方が大きく変わる・共通の決まりにかかわる）は、実装の前にユーザーに確認する
3. **実装する**。設計書に書いたことだけを作る。作っている途中で設計を変えたくなったら、先に設計書を直してから作る
4. テストと自動プレイで確かめる
5. **結果を設計書に書き戻す**: 数値表・調整の記録・わかっている問題・「確かめたか」の欄。仕様の節もいまの作りに合わせる
6. 設計書と実装は同じコミットに入れる

共通の決まり（03）にかかわる変更は、03 も同じように先に直す。

## 子どもに好まれると考えているポイント（共通）

対象は年長〜小学校低学年。これまでに調べたこと・ユーザーの指摘から、どのゲームにも当てはまりそうなものをまとめる。ゲームごとの設計書では、このうちどれをどう使うかを書く。

| ポイント | 根拠 | 気をつけること |
|---|---|---|
| 操作が1つ（動くだけ・ひっぱるだけ・タップだけ） | Vampire Survivors（入力は移動だけ）、低学年に人気のアプリはタップとドラッグだけ（04） | 字が読めなくてもわかるように、最初は手の動きなどで見せる |
| 数秒ごとに良いことが起きる | Vampire Survivors の分析（ジェム・レベルアップ・宝箱がひっきりなし） | ただし止めすぎない（下の「止まりすぎない」） |
| 弱い → とても強い | Vampire Survivors（弱い最初と、画面を埋めつくす最後） | 1回の中で成長を見せる。最後に大きな見せ場 |
| 危なさがある | ユーザーの指摘「危なくなる要素もなく作業チック」 | 最初のステージから少し危なくする |
| 危ないことには合図がある | 年長さんは速い判断が苦手 | 赤い輪・赤くなって震える・ふくらむ、など攻撃の前に見せる。理不尽にやられない |
| 敵ごとに違う | ユーザーの指摘「敵キャラそれぞれの特徴がほしい」 | 役（動きの基本）は共通にして、覚えることを増やしすぎない |
| 自分で選ぶと戦い方が変わる | ユーザーの指摘「同じ動きしかしない」、Vampire Survivors・Brotato | 持てる数に上限をつける（全部持てると選ぶ意味がない） |
| 「しんか」のような大きな瞬間 | Vampire Survivors の進化 | 条件は年長さんにもわかるくらい単純に |
| 先に進むと景色が変わる | Survivor.io の章 | 見た目が変わると「進んだ」とわかる |
| 集める・埋める | Vampire Survivors の隠し要素、図鑑 | 強さに関係しない物にすると、つりあいを崩さない |
| 止まりすぎない | ユーザーの指摘「レベルアップが頻繁すぎてテンポが悪い」 | 選ぶ画面は1回15〜20回まで |
| だらだら続かない | ユーザーの指摘「ボーナスが長すぎてダレる」 | 山場のあとはすぐ終わる。3〜7分 |
| 負けてもすぐまた遊べる | Vampire Survivors（負けてもお金がもらえる） | 参加コイン（03 6.）。負けの画面を責めない言葉に |
| 勉強で「強くなる」「選べるものが増える」 | 03 4. | コインが安すぎるとすぐ買い占められる（下の「学んだこと」） |

## バランスの考え方（共通）

- **3つの軸に分けて決める**
  - ステージ間: 推奨コイン（03 5.）→ 推奨強化レベル → 敵の強さ。1ステージ進むのに「クリア + 勉強2回」
  - 1回の中の時間: だんだん危なくなり、山場（ボスなど）がある
  - 1回の中のプレイヤーの成長: 選ぶ回数・育ち方
- **推奨より少ない強化では負ける**ことも確かめる（勉強が要る形になっているか）
- 数値は1か所（`stages.ts` など）にまとめ、テストを書く
- **自動プレイ（bot）で確かめる**。ただし次のことに気をつける
  - 同じ条件でも結果がばらつく。1つの条件を2回以上見る
  - bot と子どもは動きが違う（bot は逃げ続けるのがうまい、など）。bot の結果は目安。最後は子どもに遊んでもらって決める
  - 自動プレイ中にソースを直すと、開発サーバーがページを読み直してプレイが止まる。走らせている間はソースを触らない
- 調整したら、設計書の「調整の記録」に版ごとに書く（変えたこと・きっかけ・結果）

## これまでに学んだこと

サバイバーの改善（2026-09）で、ユーザーの指摘から学んだこと。

| 学んだこと | きっかけ |
|---|---|
| ご褒美の時間（ボーナスタイム）でも、長いとだれる | 「ボーナスが長すぎてダレるので要らないかも」 |
| レベルアップのたびに止まると、テンポが悪くなる。1回で15〜20回まで | 「レベルアップが頻繁すぎてテンポが悪い」 |
| 強化が勉強1回で1つ買えると、すぐ買い占められる。値段は上がっていく形にし、全部そろうまで数か月 | 「つよくするの各アイテムが安すぎてすぐに買い占めできてしまう」 |
| 最初のステージでも、危なくならないと作業になる | 「ステージ1の敵が弱すぎて危なくなる要素もなく作業チック」 |
| 敵は見た目だけでなく、動きや攻撃で差をつける | 「敵キャラそれぞれの特徴がほしい、例えば遠距離攻撃があるとか」 |
| 何でも持てると選ぶ意味がない。持てる数に上限を | 「なんでもかんでも装備すると意味がないので、装備できる武器は上限があったほうがいい」 |
| 永続強化は数値だけでなく「選べる物が増える」解放もよい | 03 の決まりの変更（永続強化にスキル・装備も） |
